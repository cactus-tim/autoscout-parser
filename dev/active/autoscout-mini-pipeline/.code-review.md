# Code Review: autoscout-mini-pipeline

## Mode
full

## Verdict
FINDINGS

## Summary
The implementation is broadly faithful to the plan: NESTED ScoredListing layout is consistent across pipeline.py, sheets/client.py, scoring/batch.py, and notify/telegram.py; Mode.TOOLS is locked with an enum-identity test; AsyncOpenAI is enforced; Semaphore-gated concurrency is correct; column L is the score column throughout; install.sh uses t64 variants; bootstrap and conditional formatting are idempotent; integration tests use both module-level pytestmark and fixture-level skip; all per-step files exist. The findings below are mostly documentation drift and minor configuration gaps; no critical functional bugs were observed.

## Findings

### README documents env var name that does not exist in Settings
- **Severity**: major
- **File**: `README.md:41`
- **Reference**: plan §Phase 8 (README troubleshooting) + plan acceptance gate "all env vars match Settings"
- **Issue**: README's configuration table lists `NOTIFY_THRESHOLD` as the env var name, but `Settings` (config.py) and `.env.example` both use `SCORE_NOTIFY_THRESHOLD`. A user who copies the README name into `.env` will find their threshold silently ignored (pydantic-settings extra="ignore" will swallow it).
- **Expected**: README must use the same env var name actually consumed by Settings, i.e. `SCORE_NOTIFY_THRESHOLD`.
- **Actual**: README documents `NOTIFY_THRESHOLD`; Settings field is `score_notify_threshold` (read from `SCORE_NOTIFY_THRESHOLD`).
- **Suggested Fix**: Rename the README row from `NOTIFY_THRESHOLD` to `SCORE_NOTIFY_THRESHOLD`.

### README documents LOG_LEVEL env var that Settings does not honor
- **Severity**: minor
- **File**: `README.md:45`
- **Reference**: plan §Phase 1.4 / §Phase 8 — env vars must match Settings
- **Issue**: README lists `LOG_LEVEL` as a configurable variable, but `Settings` has no such field and `logging_setup.configure_logging()` hard-codes `level=logging.INFO`. Setting `LOG_LEVEL=DEBUG` in `.env` has no effect.
- **Expected**: Either (a) add a `log_level` field to Settings and have pipeline.py pass it to `configure_logging`, or (b) drop `LOG_LEVEL` from the README config table.
- **Actual**: README claims it works; nothing reads it.
- **Suggested Fix**: Add `log_level: str = Field("INFO")` to Settings and pass it through, or remove the row from the README table.

### Pipeline does not pass throttle settings to iter_listings
- **Severity**: minor
- **File**: `src/autoscout_pipeline/pipeline.py:96`
- **Reference**: plan §3.4 — "polite throttle between pages using AS24_THROTTLE_MIN/AS24_THROTTLE_MAX"
- **Issue**: `iter_listings(SEARCH_CRITERIA)` is invoked without passing `throttle_min` / `throttle_max`, so it falls back to the function-level defaults (2.0/6.0). Operator changes to `AS24_THROTTLE_MIN`/`AS24_THROTTLE_MAX` in `.env` are ignored.
- **Expected**: Pass `throttle_min=settings.as24_throttle_min, throttle_max=settings.as24_throttle_max` to `iter_listings`.
- **Actual**: Settings values for throttle are loaded but never consumed.
- **Suggested Fix**: Update the call site in `pipeline.py` to forward both throttle settings.

### Telegram send_batch sleeps after every send (incl. last); docstring is wrong
- **Severity**: minor
- **File**: `src/autoscout_pipeline/notify/telegram.py:92-107` (docstring at 95-96)
- **Reference**: plan §6.1 — "0.5s delay" between sends
- **Issue**: The docstring states "The delay is not added after the last message," but the code unconditionally calls `await asyncio.sleep(0.5)` after each successful send, including the last one. The unit test `test_send_batch_sleeps_between_sends` asserts `sleep_mock.call_count == 3` for 3 sends, confirming the implementation sleeps N times (not N-1). Either the docstring or the implementation is wrong; based on the plan ("between consecutive sends") the implementation is the one that drifted, but the test pinned the wrong behaviour.
- **Expected**: Sleep `len(qualifying_sends) - 1` times, or update the docstring (and test) to acknowledge the post-last sleep.
- **Actual**: Sleep N times for N sends; docstring claims N-1.
- **Suggested Fix**: Either move the sleep to occur before each send except the first (and update the test to expect N-1), or change the docstring to "A 0.5-second delay is inserted after each successful send" and accept the trailing sleep.

### Smoke script will misreport scraped count when pipeline emits errors
- **Severity**: minor
- **File**: `scripts/smoke.py:198`
- **Reference**: plan §9.1 — "prints a one-line summary"
- **Issue**: `scraped = len(notes) and _extract_int(notes, "scraped=")` — `len(notes)` returns the integer string length when truthy and is the value used when falsy, so on an empty notes string this evaluates to `0`. On non-empty notes it short-circuits to the `_extract_int(...)` result. This works in the happy path but is fragile and the code reads as if the author meant `if notes else 0` and got short-circuit semantics inverted. It cannot return the wrong value here, but the construct is confusing and unintended.
- **Expected**: A direct call: `scraped = _extract_int(notes, "scraped=")`.
- **Actual**: A truthiness short-circuit that compiles to a no-op for the common case but misleads readers.
- **Suggested Fix**: Replace with `scraped = _extract_int(notes, "scraped=")`.

### Pipeline constructs SheetsClient even in dry-run, requiring real creds
- **Severity**: minor
- **File**: `src/autoscout_pipeline/pipeline.py:85-88`
- **Reference**: plan §7.1 — "--dry-run skips all writes and notifications"
- **Issue**: `SheetsClient(...)` is instantiated unconditionally; its `__init__` calls `gspread.service_account(filename=str(creds_path))` which fails immediately if `creds.json` does not exist. A user running `autoscout-pipeline --dry-run` on a fresh machine without GCP credentials cannot smoke-check the wiring without setting up a real service account.
- **Expected**: Either lazy-initialise the client only when a write is needed, or wrap the dry-run path so it bypasses Sheets construction entirely (mirroring how Telegram is gated on tg_token presence).
- **Actual**: Dry-run still requires valid `creds.json`.
- **Suggested Fix**: Make SheetsClient construction conditional on `not dry_run`, or accept an optional `client` parameter for testing.

### Test fixtures are synthetic, not real captures from autoscout24.com
- **Severity**: minor
- **File**: `tests/fixtures/autoscout_listings_page1.html`, `tests/fixtures/autoscout_listing_detail.html`
- **Reference**: plan §3.5 — "Create by running capture_fixtures.py; must be committed to repo" + context.md "Real captured HTML from autoscout24.com (post-hydration, contains __NEXT_DATA__)"
- **Issue**: The committed page1 fixture is 211 lines of hand-rolled JSON (12 listings with predictable IDs `AS24-001`..`AS24-012`); the detail fixture is similarly synthetic (`AS24-DETAIL-001`). The plan calls for capture from the live site so the parser is exercised against AutoScout's actual schema. With a synthetic fixture, the parser may pass tests but break against real `__NEXT_DATA__` payloads (e.g. unexpected key names, nested encoding, missing fields).
- **Expected**: Real captured HTML committed (per plan + context.md). The capture_fixtures.py script exists but appears not to have been run.
- **Actual**: Synthetic JSON shaped to match what the parser expects, which means the parser is being tested against itself.
- **Suggested Fix**: Either run `scripts/capture_fixtures.py` against live autoscout24.com and commit the output, or document the synthetic-fixture decision in `tests/fixtures/README.md` and revise the plan to acknowledge that schema validation against the live site is an open risk.

### Settings: required-in-prod fields default to empty string
- **Severity**: minor
- **File**: `src/autoscout_pipeline/config.py:19-23`
- **Reference**: README "Required" column states `SHEET_ID`, `TG_TOKEN`, `TG_CHAT_ID` are required
- **Issue**: `tg_token`, `tg_chat_id`, `sheet_id` use `Field("")` defaults instead of `Field(...)`. This means a misconfigured production deployment will not raise at Settings load time; it will fail later when SheetsClient tries `open_by_key("")` or notifier posts to a malformed URL. Plan said "all env vars in .env.example match Settings"; that part is met, but the README's "required" claim is unenforced.
- **Expected**: Either make these required (`Field(...)`) so misconfiguration fails fast, or revise the README to say they are optional with documented graceful-degradation behaviour.
- **Actual**: Fields silently accept `""`; sheet_id="" would fail downstream with an opaque gspread error.
- **Suggested Fix**: Change `sheet_id` to `Field(...)` (required); leave `tg_token`/`tg_chat_id` as optional empty (matches the documented "leave blank to disable notifications" behaviour) and update the README "Required" column accordingly.

### Pipeline scrape-error path may double-count errors
- **Severity**: minor
- **File**: `src/autoscout_pipeline/pipeline.py:95-101, 142-144`
- **Reference**: plan §7.2 — "scrape-error test (RunRecord.errors=1)"
- **Issue**: `EmptyResultsError` is caught locally inside the scraping block (line 98) and increments `err_count` once. If a different exception propagates out of the inner block (e.g., NextDataMissingError), the outer try/except at line 142 also increments `err_count`, so a single root cause can become `errors=1` or `errors=2` depending on which exception class was raised. For deterministic reporting the increment should happen exactly once per failed phase.
- **Expected**: Single, well-defined accounting per failed phase.
- **Actual**: Different exception types yield different `errors` counts.
- **Suggested Fix**: Either move all error counting to the outer except, or add a comment clarifying the inner/outer responsibility split (and verify the test scenario covers both paths).
